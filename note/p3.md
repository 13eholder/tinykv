

TinyKV总体设计

![TinyKV](./imgs/TinyKV.png)

TinyKV 的处理流程如下：

* TinyKV Server 通过 gRPC 接口接收客户端的请求req,是系统的 kv 服务入口。
* raftStorage 在raft_server 中,是 Raft 状态机与 kv 服务之间的中间层。实现了 Storage 接口,在接口中将请求封装成 RaftCmdRequest。在 raftRouter 中将请求发送到对应的peer。
* raftStore 是 raft 的核心部分。包含两个需要关注的部分。
  * raftWorker：轮询处理来自RaftStorage的请求,驱动Raft状态机处理日志复制、心跳等逻辑。
  * peerStorage 管理持久化元数据（如RaftLocalState、RaftApplyState）,负责Raft日志应用和状态持久化存储（通过raftdb和kvdb）。
* raftRawNode 接收 peerStorage 的操作以及 step,返回 ready. peerStorage 将 raft 相关的数据持久化,转发 raft 节点的msgs,并将已提交的日志进行应用。peer 即可调用 raftRawNode 的 advance() 更新 raft 的状态。在peerStorage 中 RaftCmdRequest 后的结果,将封装成 RaftCmdResponse 结构体返回给 RaftStorage

一个TinyKV Server可以承载多个Peer,多个Peer共用底层的存储引擎(badger.DB),但是不同的Peer有自己的RaftNode,属于不同的Region,region是逻辑概念,本质上是`RaftGroup + [StartKey,EndKey)`, 一个Region中有多个不同的Peer,分布在不同的TinyKV Server,一个Peer属于一个Region;这样设计有效地分散请求,便于进行负载均衡,同时利于进行scan操作
